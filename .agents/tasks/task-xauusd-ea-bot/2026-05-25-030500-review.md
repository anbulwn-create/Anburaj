# Multi-factor XAUUSD Expert Advisor with SMC, hidden trailing, and news filter

A greenfield ~4,700-line MQL5 Expert Advisor for Gold trading on M5 with H1 trend confirmation. The architecture splits concerns into seven modules: signal generation (EMA + RSI + Smart Money Concepts), risk management (Kelly criterion, drawdown limits, equity curve), trade execution with retry logic, six trailing stop modes including a hidden lock-in to avoid broker stop-hunting, and a static news calendar. The design is modular by MQL5 standards, with include guards, proper indicator handle lifecycle, and consistent logging.

**Watch for:** Signal scoring calls `IsPriceAtOrderBlock` and `IsPriceInFVG` as side-effect-bearing queries that mutate zone state on every signal evaluation, not just on trade entry (confirmed). The `IsNewBar` utility uses a single static variable shared across all callers, making it unsafe if called for multiple timeframes (confirmed). The partial-close tracking mechanism is broken because MT5 cannot modify position comments post-open, so repeated partial closes will fire on every tick (confirmed). Hidden stop data for closed positions is never cleaned up, causing unbounded array growth (confirmed).

## High-level view

The signal engine combines three independent scoring subsystems (EMA, RSI, SMC) into a weighted composite score ranging from -100 to +100. A composite threshold of 30 triggers entries. The SMC scoring has state-mutation side effects that will alter zone validity every time a signal is evaluated, not only when a trade fires. Additionally, setting all signal weights to zero causes a division-by-zero crash.

Risk management implements percentage-based lot sizing, Kelly criterion (gated behind a 20-trade minimum), drawdown limits, daily loss limits, equity curve filtering, and consecutive-loss lot reduction.

Trade execution uses MT5's standard library `CTrade` with FOK filling (which is not universally broker-supported), retry logic for transient errors, and proper fatal-error bailouts. The partial close manager cannot reliably mark positions as "done" because the code acknowledges MT5 doesn't allow post-open comment modification but provides no alternative tracking, resulting in repeated closes on every tick.

The trailing stop subsystem offers six modes routed through a single `ManageTrailing` entry point. The hidden lock-in mode maintains an internal SL that only syncs to the server at 2x trail distance steps. However, the `m_hiddenStops` array grows monotonically because `RemoveHiddenStop` is never called after positions close.

The news filter relies on a hardcoded approximate schedule rather than the MQL5 economic calendar API. Events that shift days (e.g., NFP delayed by a holiday) will be missed.

<summary>Issues (10)</summary>

1. **SMC zone mutation in signal scoring** — `GetSMCScore()` calls `IsPriceAtOrderBlock` and `IsPriceInFVG`, both of which increment touch counts and invalidate zones. Move mutation to a separate "consume zone" step that fires only on trade entry, or split the query from the mutation. (confirmed)
2. **IsNewBar single-static hazard** — The `IsNewBar` function in Utils.mqh uses one static `lastBarTime` variable. If called for M5 and H1, it will misfire. Replace with a per-timeframe map or move bar tracking into each module. (confirmed)
3. **Partial close fires repeatedly** — `ManagePartialClose` checks `StringFind(posComment, "[PC]")` but never writes `[PC]`. Use an internal ticket set to track which positions have been partially closed. (confirmed)
4. **Hidden stop data leaks** — `AddHiddenStop` is called for every tracked position if not found, and `RemoveHiddenStop` is never invoked after positions close. Add cleanup logic keyed to `OnTradeTransaction` or periodic pruning. (confirmed)
5. **RSI divergence is naive** — Comparing bar 0 vs bar 10 directly (not actual swing lows/highs) produces frequent false positives in ranging markets. Find actual swing lows within the lookback window. (likely)
6. **Equity history O(n) shift on every timer tick** — `UpdateEquityHistory` shifts 100 elements once per second. Use a circular buffer index. (confirmed)
7. **Signal weight division by zero** — `SetWeights` stores weights without validation. All weights set to 0 causes division by zero in `GenerateSignal`. Add a guard or minimum total weight. (confirmed)
8. **Order filling mode hardcoded to FOK** — `ORDER_FILLING_FOK` is not supported by all brokers. Detect allowed filling mode via `SYMBOL_FILLING_MODE` and fall back to IOC. (confirmed)
9. **No SL/TP adaptation from SMC** — The EA always uses fixed `InpDefaultSLPips`/`InpDefaultTPPips` regardless of detected order blocks or structure. Pass structure-based levels from the signal engine to `ExecuteTrade`. (confirmed)
10. **BOS and CHoCH can fire on same bar** — Both flags can be set simultaneously when structure flips rapidly, producing contradictory signals. Consider making them mutually exclusive per update cycle. (likely)

## SMC zone state mutation during signal evaluation

`GetSMCScore()` in SignalEngine.mqh calls three methods on `CSMCAnalysis` that modify internal state:

```cpp
if(m_smcAnalysis.IsPriceAtOrderBlock(price, isBullish))  // increments touchCount, may invalidate
if(m_smcAnalysis.IsPriceInFVG(price, isBullish))          // sets isValid = false (FVG "filled")
if(m_smcAnalysis.IsLiquiditySweep(price))                  // sets isValid = false
```

These fire on every new bar regardless of whether a trade is taken. An order block with `touchCount >= 3` will be invalidated after three signal evaluations even if no trade entered at that level. FVG zones are consumed on first signal evaluation touching them, making them unavailable for actual trade entry logic on the next bar.

The fix: split query methods from consume methods. `IsPriceAtOrderBlock` should be a pure query, with a separate `ConsumeOrderBlock` called only after successful trade entry.

## Partial close tracking is non-functional

`ManagePartialClose` in TradeManager.mqh searches for `[PC]` in the position comment to determine if a partial close has already occurred:

```cpp
string posComment = m_position.Comment();
if(StringFind(posComment, "[PC]") < 0)
{
   if(PartialClose(ticket, m_partialClosePercent))
   {
      // Note: MT5 doesn't allow comment modification directly
   }
}
```

Since the comment is never modified, the partial close fires on every tick after the profit threshold is reached. Each subsequent call closes `m_partialClosePercent` of the *remaining* volume, rapidly draining the position in exponential decay until it hits minimum lot.

Fix: maintain a `ulong m_partialClosedTickets[]` array checked before executing the close.

## Hidden stop data accumulates without cleanup

`CTrailingStop::ManageTrailing` adds a `HiddenStopData` entry for every tracked position. When a position closes, the corresponding entry is never removed. `RemoveHiddenStop` exists but is only called from `RemoveAllTracking` (EA shutdown). Over a long-running session, the linear scan in `FindHiddenStop` degrades and memory grows unbounded.

## Signal weights division by zero

```cpp
double totalWeight = m_weightEMA + m_weightRSI + m_weightSMC;
double compositeScore = (emaScore * m_weightEMA + rsiScore * m_weightRSI + smcScore * m_weightSMC) / totalWeight;
```

No guard against `totalWeight == 0`. The input parameters are exposed to the user and all three can be set to 0.

## BOS and CHoCH mutual exclusion

`DetectBOS` and `DetectCHoCH` are called sequentially in `CSMCAnalysis::Update()`. Both check `currentClose > m_lastSwingHigh` but under opposite `m_isBullishStructure` conditions. CHoCH flips `m_isBullishStructure`, so on bars where structure flips, BOS runs with the old state (no match), then CHoCH fires and flips. On the *next* bar, BOS may immediately fire with the new state, producing both flags active within one update cycle depending on price action. The simultaneous presence of `HasBOS() == true` and `HasCHoCH() == true` (from a prior bar since both are reset at the top of their methods) is unlikely but worth guarding against.

## No dynamic SL/TP from market structure

```cpp
double slPips = InpDefaultSLPips;  // Always 50 pips
double tpPips = InpDefaultTPPips;  // Always 100 pips
```

Despite the SMC engine detecting order blocks, FVG zones, and liquidity levels that could inform stop placement, none of this information flows into the SL/TP calculation. Adding a `suggestedSL`/`suggestedTP` field to `SignalResult` and populating it from the nearest opposing structure zone would substantially improve adaptability to varying volatility.

## Order filling mode compatibility

```cpp
m_trade.SetTypeFilling(ORDER_FILLING_FOK);
```

FOK (Fill or Kill) is not universally available. Many brokers (especially those using the exchange execution model) only support IOC or RETURN. Query `SymbolInfoInteger(_Symbol, SYMBOL_FILLING_MODE)` and select the appropriate mode.

## IsNewBar shared static

```cpp
bool IsNewBar(ENUM_TIMEFRAMES timeframe)
{
   static datetime lastBarTime = 0;  // Single static shared across all callers
   ...
}
```

The main EA avoids this function (maintains its own `g_lastBarTime`), so the risk is latent. It will break as soon as any module calls `IsNewBar` for a different timeframe. The function should use a static array indexed by timeframe, or each module should track its own bar time.

## RSI divergence detection

The divergence logic compares the current bar's price/RSI directly against bar 10:

```cpp
double priceLow1 = iLow(m_symbol, m_lowerTF, 0);
double priceLow2 = iLow(m_symbol, m_lowerTF, 10);
double rsiLow1 = rsi[0];
double rsiLow2 = rsi[10];
if(priceLow1 < priceLow2 && rsiLow1 > rsiLow2) return true;
```

This doesn't verify that bars 0 and 10 are actual swing lows. In a downtrend, every bar's low may be below bar-10's low with RSI diverging, producing persistent false-positive divergence signals. A proper implementation would find confirmed swing lows (using the swing detection logic already in SMCAnalysis) and compare those specific points.
